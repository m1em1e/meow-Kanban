# MeowKanban 数据库设计文档

## 1. 文档说明

本文档基于当前看板原型拟定，默认数据库为 SQLite，并兼顾后续迁移到 MySQL 的可行性。

设计目标：

- 支持看板、分区、任务、成员、标签、评论、附件和活动日志。
- 保持表结构轻量，优先满足单机和小团队使用。
- 使用软删除字段保护用户数据。
- 预留审计字段，便于后续统计和问题排查。
- 不创建数据库级外键约束，所有关联字段仅作为逻辑外键，由服务层校验关联有效性。

## 2. 命名约定

- 表名使用 `mk_` 前缀。
- 主键统一使用 `id`。
- 时间字段使用 `created_time`、`updated_time`、`deleted_time`。
- 软删除字段使用 `deleted`，`0` 表示未删除，`1` 表示已删除。
- 排序字段使用 `sort_order`。
- SQLite 中布尔值使用 `INTEGER` 存储，`0` 为 false，`1` 为 true。
- `xxx_id` 字段只表示逻辑关联，不在建表 SQL 中声明 `FOREIGN KEY`。

## 3. 实体关系概览

以下关系为业务逻辑关系，不表示数据库物理外键约束。

```text
mk_user 1 --- n mk_board
mk_user n --- n mk_board 通过 mk_board_member
mk_board 1 --- n mk_board_section
mk_board 1 --- n mk_task
mk_board_section 1 --- n mk_task
mk_task n --- n mk_tag 通过 mk_task_tag
mk_task 1 --- n mk_task_comment
mk_task 1 --- n mk_task_attachment
mk_task 1 --- n mk_task_activity
mk_user 1 --- n mk_user_preference
```

## 4. 表结构设计

### 4.1 用户表 `mk_user`

存储登录用户和成员基础信息。

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | INTEGER | 是 | 自增 | 主键 |
| `username` | VARCHAR(50) | 是 |  | 登录名，唯一 |
| `password` | VARCHAR(255) | 是 |  | 密码哈希 |
| `salt` | VARCHAR(100) | 是 |  | 密码盐 |
| `nickname` | VARCHAR(50) | 是 |  | 昵称 |
| `email` | VARCHAR(120) | 否 |  | 邮箱，唯一 |
| `avatar` | VARCHAR(500) | 否 |  | 头像图片地址或存储路径；为空时由展示层根据 `nickname` 生成默认头像 |
| `status` | VARCHAR(20) | 是 | `active` | `active` / `disabled` |
| `last_login_time` | DATETIME | 否 |  | 最后登录时间 |
| `created_time` | DATETIME | 是 | 当前时间 | 创建时间 |
| `updated_time` | DATETIME | 是 | 当前时间 | 更新时间 |
| `deleted` | INTEGER | 是 | `0` | 是否删除 |
| `deleted_time` | DATETIME | 否 |  | 删除时间 |

索引：

```sql
CREATE UNIQUE INDEX uk_mk_user_username ON mk_user(username);
CREATE UNIQUE INDEX uk_mk_user_email ON mk_user(email);
```

## 6. 初始化数据建议

创建默认看板后，初始化以下分区：

| code | title | sort_order |
| --- | --- | --- |
| `backlog` | 待规划 | 10 |
| `todo` | 待处理 | 20 |
| `doing` | 进行中 | 30 |
| `review` | 验收 | 40 |
| `done` | 完成 | 50 |

原型任务可作为开发环境种子数据，用于验证列表、筛选、拖拽和详情抽屉。

## 7. 数据约束建议

### 7.1 逻辑外键校验

数据库表只保存 `xxx_id` 关联字段，不声明物理外键。服务层在写入和更新时负责校验：

- 创建看板时，`owner_id` 对应用户必须存在且未删除。
- 创建成员关系时，`board_id` 和 `user_id` 必须存在且未删除。
- 创建或移动任务时，`board_id`、`section_id`、`owner_id` 必须在业务范围内有效。
- 删除分区、任务、标签时，由服务层决定迁移、软删除或拒绝操作。
- 查询时通过业务条件过滤 `deleted = 0`，避免逻辑删除数据被误关联。

这样可以降低数据库迁移成本，也能避免软删除、批量导入、数据恢复和单机部署场景被物理外键约束阻塞。

### 7.2 任务编号生成

任务编号建议按看板生成：

```text
MK-自增序号
```

可先在服务端创建任务时查询当前看板最大编号并递增。后续多人并发场景下，建议增加独立序列表或使用数据库事务保证唯一。

### 7.3 分区删除

删除分区前必须满足以下条件之一：

- 分区内没有未删除任务。
- 请求提供 `fallback_section_id`，服务端将任务迁移到目标分区。

至少保留一个未删除分区。

### 7.4 任务流转

任务流转只修改 `section_id` 和 `sort_order`，并写入 `mk_task_activity`。

详情抽屉“上一步 / 下一步”根据 `mk_board_section.sort_order` 计算相邻分区。

### 7.5 搜索与筛选

任务列表搜索范围建议包含：

- `task_no`
- `title`
- `description`
- `owner.nickname`
- `tag.name`

SQLite 早期可使用 `LIKE` 查询；后续任务量较大时，可评估 FTS5 全文索引。

## 8. MyBatis-Plus 映射建议

项目已引入 MyBatis-Plus，建议实体统一继承或组合以下审计字段：

| Java 字段 | 数据库字段 | 说明 |
| --- | --- | --- |
| `createdTime` | `created_time` | 创建时间 |
| `updatedTime` | `updated_time` | 更新时间 |
| `deleted` | `deleted` | 逻辑删除 |

## 9. MVP 落库顺序

建议按以下顺序实现数据库迁移和实体：

1. `mk_user`
2. `mk_board`
3. `mk_board_member`
4. `mk_board_section`

## 10. 后续扩展

- 看板模板：为不同项目类型提供默认分区和任务模板。
- 任务检查清单：支持任务内子项。
- 任务依赖：支持阻塞关系和前置任务。
- 通知表：支持到期提醒、成员提及和状态变更提醒。
- 审计日志：独立记录看板、成员、权限等非任务操作。
- 多数据库兼容：为 MySQL 增加 Flyway 或 Liquibase 迁移脚本。
